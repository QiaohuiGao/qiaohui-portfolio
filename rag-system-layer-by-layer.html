Designing a RAG System, Layer by Layer

The pipeline behind a production system, and the question worth asking at each layer.

Written by Bonnie GaoSystems · Retrieval · Production AI

Most explanations of retrieval-augmented generation stop at four steps. Chunk your documents, embed them, retrieve the nearest ones, stuff them into a prompt. That description is not wrong, it is just incomplete in the way a floor plan is incomplete for a building. It tells you the rooms exist without telling you which walls are load-bearing.

I spent a long stretch working through what a production-grade version of this system actually requires, going layer by layer rather than treating “RAG” as one monolithic thing. What follows is a summary of that process, organized the way I now think about it. Each layer gets one core question, the one that in my experience separates a demo from something that survives contact with real data and real users.

The principle underneath everything

Let constraints choose the architecture.

Before any layer-by-layer breakdown, one idea kept resurfacing enough that it earned the status of a rule I check every decision against. Architecture should be derived from latency requirements and cost ceilings, not from whichever technology looks most sophisticated. Every time I saw a design go wrong, in my own drafts or in systems I studied, the root cause traced back to a technology chosen before the constraints were pinned down. Ask first how much staleness the users can tolerate and what the budget actually allows. Everything downstream—batch versus streaming, self-hosted models versus an API, a dedicated vector database versus a simple extension on Postgres—falls out of that answer.

01

Ingestion

What happens when a source changes without telling you cleanly?

Every external data source eventually misbehaves. Rate limits, inconsistent formats, permission models that do not map cleanly onto anything you control. The mistake I kept catching myself making early on was treating ingestion as a one-time script rather than a long-lived adapter with its own failure modes.

A connector for each source, a shared rate-limiting layer instead of one bolted onto each connector separately, and a habit that took me longer to internalize than it should have: permission metadata has to be captured at the same moment as content, not reconstructed later. If a document has an access list in its source system, that list needs to travel with it from the very first fetch. Bolting permission checks on after the fact almost always leaves a gap somewhere, and that gap is exactly the kind of thing that turns into a real incident.

02

The control plane

How do you know something changed without reprocessing everything?

This is the layer most tutorials skip and the one that determines whether a system can survive real scale. Once a corpus is large enough that reprocessing all of it on every run is not viable, you need a cheap, fast way to decide what actually needs expensive work.

I settled on a two-tier check. A version number from the source system is nearly free to compare but not fully trustworthy, since a save event does not always mean the content meaningfully changed. A content hash computed after normalization is trustworthy but costs a fetch and a parse to compute. Check the cheap signal first, only fall through to the expensive one when it disagrees.

The other lesson here took a failed assumption to learn properly. State cannot be binary. A batch job that partially completes—some chunks embedded and others not—needs a state that is neither success nor failure, or the rest of the system will quietly trust a document that is not actually ready.

03

Extraction & normalization

What does the pipeline look like once you stop caring where content came from?

Heterogeneous sources are inevitable. HTML pages, PDFs, slide decks, images. The trap is writing separate downstream logic for each. A canonical intermediate representation—a single schema that every source format gets converted into before chunking ever touches it—is what keeps the rest of the pipeline from multiplying in complexity every time a new source type shows up.

This layer is unglamorous and easy to underinvest in, which is exactly why it tends to be where things quietly break.

04

Chunking

What should the actual unit of retrieval be?

A chunk is not a token budget problem, it is a retrieval unit, and those are different design goals. Fixed-length splitting is the fastest way to a working prototype and the fastest way to a ceiling on quality, since it ignores every structural and semantic boundary in the source text. Structure-aware and semantic splitting close part of that gap.

The part that took the longest to actually understand, rather than just name, is what happens at the edges between chunks. An entity introduced in one paragraph and referenced only by pronoun in the next will lose that connection the moment a splitter draws a line between them. Newer techniques—generating a short contextual note for each chunk before embedding it, or encoding the full document first and only splitting afterward—exist because this problem does not have a clean solution otherwise.

The other habit worth building here is measuring chunk stability, not just retrieval accuracy. A strategy where a one-line edit reshuffles every downstream chunk boundary is expensive in ways that only show up once you are running incremental updates in production, not during a one-time evaluation run.

A chunk is not a token budget problem. It is a retrieval unit.
05

Embedding

What happens the day you need to change the model?

An embedding model defines the geometry that similarity search depends on. Two models, even two versions of the same model, do not generally produce vectors that can be compared to each other, which means an upgrade is not an addition, it is a full recomputation of the entire index.

I did not appreciate how expensive that fact is until I worked through what a real migration requires. Build the new index in the shadow of the old one, validate it offline before it touches any real traffic, keep both writable during the transition so the new index does not fall behind while the old one is still backfilling, and only then cut traffic over, with a rollback window kept open in case something the offline evaluation missed shows up in production.

06

Indexing & the vector store

Where does permission enforcement actually have to live?

Writing vectors straight into a database from application code looks fine until you need version isolation between an old and new embedding model, a way to retry a failed write without duplicating it, or a soft delete you can actually audit. All of that argues for a dedicated indexing layer rather than a direct write path.

The sharper lesson, though, is about access control. Permission filtering has to be part of the vector search query itself, not something applied to results after they come back. The difference matters because what gets filtered out here is not irrelevant content, it is content a user has no right to see, and letting it pass through application memory even briefly before being discarded is a real exposure surface, not a theoretical one.

07

Retrieval & generation

Which of three failure modes are you actually looking at?

This is the layer that gets the most attention and the one I found most useful to organize around a simple taxonomy rather than a list of techniques. Every disappointing answer traces back to one of three failures.

Retrieval failureThe right content was never found.
Augmentation failureThe content was found but not used well.
Generation failureThe model had what it needed and still got it wrong.

Naming which failure you are looking at before reaching for a fix changed how I approached this layer entirely. Query rewriting and hypothetical document embeddings address retrieval failure by closing the gap between how a question is phrased and how the answer is written. Reranking and context reordering address augmentation failure. Grounding constraints, citation requirements, and confidence-gated refusal address generation failure.

And for the harder cases—questions that need more than one hop of reasoning, or where retrieval quality itself is unreliable enough that it needs a correction step—static retrieve-then-generate stops being enough and the system needs to decide dynamically whether to retrieve again, or route to a different source entirely.

Across every layer

Reliability & evaluation

A pipeline that runs is not the same as a pipeline that recovers. Idempotent writes, so a retried task does not double up its effects. Explicit partial-failure states, so a half-finished update never gets treated as a finished one. And underneath all of it, evaluation that is specific enough to catch a regression rather than vague enough to always look fine.

Recall at k for whether retrieval is working. Faithfulness for whether the generated answer actually stays inside what was retrieved. A small, continuously growing set of real questions with known good answers, mined from real usage rather than written once and left static, has been the single highest-leverage thing I built at this layer, because everything else in the system gets judged against it.

What actually stuck

Design for the day after launch.

The layer-by-layer view is useful, but the thing I keep coming back to is smaller than any single layer. Every one of these problems—staleness, structural loss at boundaries, semantic drift between versions, silent security gaps—is a version of the same underlying question: what happens when the world changes after you have already built something on top of it?

A system that only works on the day it was built is a demo. A system that keeps working as its inputs, models, and users change is the actual engineering problem, and it is the one worth designing for from the first layer onward.
